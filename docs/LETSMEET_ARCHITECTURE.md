# LeTsMeet Architecture

## 1. System architecture

LeTsMeet is designed as a multi-tenant SaaS conferencing platform built around a React + TypeScript client, a Supabase Postgres data layer, and a LiveKit media plane. The platform is structured so that user identity, org/workspace membership, meeting records, and authorization all live in the database, while LiveKit token issuance remains server-side and policy-driven.

At a high level:

- Frontend: React application served by Vite, protected by Supabase Auth session state.
- Data layer: Supabase Postgres with RLS and tenant-aware policies.
- Media layer: LiveKit SFU for real-time audio/video and screen sharing.
- Token service: Express service that validates authenticated users and room access before issuing a LiveKit JWT.
- Storage: Supabase-managed data storage for relational records and future object storage for meeting artifacts.
- Future services: recording workers, transcription, AI summarization, analytics, notifications, and background jobs.

## 2. Frontend architecture

The frontend is intentionally modular and keeps business logic out of view components. The app should favor typed data-access helpers over ad hoc supabase calls. The current phase-1 structure is centered on:

- Auth context: current user, session loading state, sign in/out, and organization/workspace selection.
- Route-level protection: protected pages redirect unauthenticated users to auth.
- Page components: authentication, home dashboard, scheduling, join flow, meeting room, and settings.
- Shared utilities: secure meeting code generation, tenant helpers, and Supabase query wrappers.

The frontend must remain browser-safe and must never own authorization decisions. It can display only data it is allowed to read. It should treat the database as the source of truth for all persistent meeting and tenant data.

## 3. Backend architecture

The current backend is intentionally small but strategically important. The token endpoint is the trust boundary between the browser and the media layer.

Responsibilities of the backend include:

- validating the user’s bearer token
- checking the meeting’s existence and room code
- confirming the caller belongs to the relevant organization/workspace
- enforcing host/co-host capabilities through role checks
- issuing an Expiring LiveKit access token with least-privilege grants
- limiting allowed origins and rejecting unauthorized room names

This protects the LiveKit infrastructure from user-controlled room selection and prevents arbitrary access to other organizations’ meetings.

## 4. Database architecture

The SaaS foundation is modeled as a multi-tenant relational schema with an explicit separation between:

- users
- organizations
- organization membership
- workspaces
- subscriptions
- usage tracking
- meetings
- scheduled meetings
- participants
- chat data
- invites

The database model supports a real meeting lifecycle and an organization-aware authorization model. Every table that contains business data must be scoped by tenant context or by an explicit ownership relationship.

Key goals:

- tenant isolation via RLS
- explicit meeting identity using UUIDs and human-friendly codes
- organization-aware meeting ownership
- distinct workspace-level separation for teams and departments
- future usage enforcement hooks for plans and quotas

## 5. Authentication model

Authentication is handled through Supabase Auth. The app relies on session state and user identity from auth.users.

The following should remain true:

- the frontend never stores a service role key
- only signed-in users can create or access sensitive meeting state
- each authenticated session must be verified before LiveKit access is granted
- user provisioning occurs on login or first access so application data stays aligned with the auth table

The app must not trust client-provided roles or user-controlled state. It should always read current authorization from the database and auth context.

## 6. Authorization model

Authorization is database-first and tenant-aware.

The base model is:

- a user belongs to one or more organizations through organization_members
- the user can have a role such as owner, admin, member, or guest
- each workspace belongs to an organization
- meetings and scheduling records are owned by a workspace and organization context
- participants are tied to a meeting and user identity when appropriate

RLS should enforce the rule that users can only access rows belonging to organizations they are a member of. Rows must not be visible to other organizations, even if the user knows the meeting code or identifier.

## 7. LiveKit architecture

LiveKit is the real-time media layer. It is not the source of truth for tenant access. Instead, it receives short-lived, least-privilege JWTs generated by the backend after authorization checks pass.

The token server should:

- read the bearer token from the request
- validate it using the Supabase auth service
- resolve the meeting record against the meeting code
- confirm the user is a member of the meeting’s organization/workspace
- issue a token with room join and publish/subscribe permissions that map to the user’s role or meeting state
- set a bounded expiration window

This architecture prevents arbitrary room hijacking and keeps room names tied to actual database records.

## 8. Meeting lifecycle

A meeting should pass through a clear database lifecycle:

- scheduled: planned future meeting with optional agenda metadata
- live: started and active in the room
- ended: completed after host shutdown or timeout
- cancelled: intentionally canceled before or during a meeting

The lifecycle fields should be tracked with timestamps and status metadata. Meeting records should not be ephemeral or stored only in local browser state.

## 9. Participant lifecycle

Participant membership should be persisted when users join a meeting and updated when they leave or are removed. The system should track:

- user identity when available
- display name
- join/leave timestamps
- host or co-host role
- admission or waiting-room state
- mute state and moderation status in future versions

This becomes the foundation for attendance, moderation, and history features.

## 10. Organization/workspace model

The organization layer is the top-level SaaS boundary. Workspaces divide an organization into logical domains such as product, sales, or operations.

Recommended model:

- org owns billing, admins, usage, and company-level policies
- workspace owns meetings, team collaboration, and room membership
- members join orgs and then get workspace-specific access
- usage limits and plan enforcement are evaluated at the organization or workspace level

This is the correct model for enterprise SaaS and for later subscription enforcement.

## 11. Security model

LeTsMeet should treat security as a first-class architecture concern.

Controls to implement:

- server-side validation of meeting codes and room names
- tenant-scoped RLS for all relevant tables
- no public read access to meetings, participants, invites, or chat data across orgs
- no client-provided role trust
- no service-role credentials in frontend bundles
- no secret values committed to source control
- restricted CORS for the token server
- secure random generation for meeting IDs and codes
- JWT verification before LiveKit token issuance

Any policy permitting unrestricted access to core meeting and participant data should be removed or tightened.

## 12. Scalability model

The foundation is designed to scale in layers:

- DB can handle relational tenant membership and meeting records
- LiveKit handles media traffic and participant connectivity
- Redis can support real-time coordination, rate limiting, and presence in later stages
- background workers can handle recordings, transcripts, and AI summaries
- object storage can hold recordings, transcripts, and uploaded artifacts

This keeps the initial application fast while remaining compatible with high concurrency and larger meeting sizes.

## 13. Future recording architecture

Recording will likely use a dedicated job pipeline:

- start record command from host or bot logic
- LiveKit emits a stream to a recording service or outbound worker
- the resulting artifact is stored in object storage
- metadata is saved back to the database
- access and retention are tied to organization/workspace policies

This should remain separate from active meeting logic so the core conferencing path is not blocked by storage-heavy workflows.

## 14. Future transcription architecture

Transcription can be implemented as an event-driven pipeline:

- capture audio streams for a live meeting
- send segments to a speech-to-text service
- store transcripts in a searchable table or blob-store pattern
- attach transcript metadata to the meeting record
- provide search and timeline access in the frontend and admin tooling

This should be subject to user consent and organization policies, especially for enterprise deployments.

## 15. Future AI architecture

AI meeting intelligence should be additive and clearly optional. The system should not imply AI features that are not functioning.

Planned AI components:

- meeting summary generation
- action item extraction
- question and answer indexing
- assistant with retrieval over transcript history
- achievement of recaps, notes, and knowledge discovery

The AI layer must respect tenant boundaries and not train across organizations without membership/consent controls.

## 16. Deployment architecture

Production deployment should separate concerns for resilience and scale:

- web app: Vite/React static frontend or CDN-hosted app
- API layer: token service and future REST/websocket endpoints
- DB: managed Supabase Postgres
- media: LiveKit cluster with supported network and TURN setup
- storage: object store for recordings and transcripts
- monitoring: logs, metrics, traces, error capture

This architecture supports a gradual path from local development to production-grade SaaS hosting.

## 17. Observability strategy

LeTsMeet needs operational visibility across database, auth, media, and app performance.

Recommended observability:

- structured server logs for token issuance and auth failures
- database query timing and RLS diagnostics
- error capture for frontend failures and route errors
- media connection logs for LiveKit room status and reconnect behavior
- usage metrics and meeting lifecycle stats for every organization/workspace

This enables debugging and supports enterprise operational standards.

## 18. Testing strategy

Testing must be real and behavior-oriented.

Priority areas:

- meeting code generation and validation
- tenant authorization rules
- LiveKit token validation and permission mapping
- meeting scheduling and lifecycle update logic
- dashboard and workspace selection flows
- protection against unsafe room codes and unauthorized access

Use a combination of unit tests for core logic and integration-style tests for critical authorization flows. Do not rely on UI-only tests for security-sensitive logic.
